# 解析与清洗

本文是第三部分的第一篇正文，它讲清从原始文档到纯文本这一段的处理。全文分为五节，前两节讲解析，中间两节讲清洗与去重，最后一节给出反例与练习。

## 一、为什么要解析

### 1.1 原始文档的问题

知识库里的文档并不整齐。运营同学可能丢来一份 Markdown，也可能丢来一份 PDF，甚至可能丢来一张扫描件。这些格式对人有意义，对程序却没有直接意义。一份 PDF 里，标题、正文、表格、页眉、页脚是混在一起的；一张扫描件里，文字甚至还不是字符，而是一堆像素。

因此，系统在入库之前必须先做一次**解析（Parsing）**。解析的任务是把各种格式的文档还原成结构化的元素，例如标题、段落、列表项与表格。只有还原出结构，系统才能知道哪一段是标题、哪一段是正文，进而做出合理的切块。

### 1.2 本项目的解析路径

本项目在 `app/retrieval/unstructured_parser.py` 中使用开源的 Unstructured 库，按文件类型分流。它支持 Markdown、PDF、DOCX、PPTX、HTML 以及常见图片。解析时，它把 `Title` 元素当作章节名，把 `NarrativeText` 与 `ListItem` 聚成段落，把 `Table` 整块保留，把 `Header`、`Footer` 与 `PageBreak` 丢弃。对 PDF 与图片，它使用自动策略，并在需要时调用 OCR，语言设置为 `chi_sim+eng`。

这里有一个必须讲清的取舍。Unstructured 被放在可选依赖 `.[docs]` 里，它不进入主依赖。当系统运行在测试环境，或者没有安装这个可选依赖时，Markdown 会退回按标题切分，其它格式则直接跳过。这条降级路径是为了让单元测试不需要下载 OCR 模型，但读者必须明白：降级路径不是 Unstructured，不能把它写进简历。本项目也从未接入 Unstructured 的云服务。

## 二、解析之后为什么还要清洗

解析只能还原结构，它管不了字符层面的噪声。原始文档里常见的噪声有几类：第一类是编码噪声，例如 Markdown 文件开头的 BOM 字节；第二类是不可见字符，例如零宽空格与软连字符；第三类是字符形态不统一，例如全角数字与半角数字；第四类是空白混乱，例如行内连续空格与多余空行。

这些噪声单独看都很小，合在一起却会伤害检索。一个全角的"７天"与一个半角的"7天"，在程序看来是两个不同的字符串；零宽字符会让一段本来连续的文本在切分时断开。系统因此在切片之后、向量化之前插入一次清洗。

## 三、清洗都做了哪些事

`app/retrieval/cleaning.py` 中的 `normalize_text` 依次完成五项操作。它先去除零宽字符与软连字符，再对文本做 NFKC 归一化，也就是把全角字符转换成半角、把兼容字符转换成标准字符。接着它删除除换行与制表符之外的控制字符。然后它判断是否拼接硬换行：当一段正文里的汉字被单个换行切开时，它把换行去掉，把汉字重新拼回，但表格不拼。最后它把行内空白压成单个空格，并把连续空行压缩到最多两个。

这套操作里有两处细节值得读者留意。第一处是 NFKC 只统一字符形态，它会把"７天"变成"7天"，但**不会**把"七天"变成"7天"，因为后者是语义改写，不属于字符归一。第二处是硬换行只对正文拼接，表格里的换行是结构的一部分，不能被去掉。

## 四、去重与脱敏

### 4.1 两级去重

清洗之后，系统还要处理重复内容。`dedupe_chunks` 做两级判断。第一级是精确去重，它计算每段内容的 SHA1，遇到相同哈希时只保留第一条，其余丢弃。第二级是近似去重，它计算每段内容的 SimHash，当两段内容的汉明距离不超过阈值时，只记录一条日志，**不**丢弃。系统之所以对近似重复只记日志而不丢弃，是因为总则与品类例外本来就该同时被召回：它们文字相近，但适用范围不同，丢掉任何一条都可能让某类问题失去依据。

### 4.2 脱敏的边界

清洗流程还会对非 Markdown 来源的内容调用 `mask_pii`，屏蔽电话、身份证、银行卡与订单号。这里有一条容易误解的边界：政策 Markdown 文件不做脱敏，因为政策文里出现的"身份证"是规则名词，不是某个用户的真实号码。脱敏的边界必须按来源区分，否则会把规则本身也屏蔽掉，破坏政策文本的完整性。

## 五、反例与练习

假设系统省略清洗，直接对原始文本切块。一份从 Word 导出的政策文档里，"退货政策"四个字之间可能夹着零宽字符，系统在切分时会把它们当成不同的词；一段正文里的全角"７天"会与查询里的半角"7天"对不上，关键词检索因此漏召回。这个反例说明，清洗看似琐碎，却是检索质量的下限保障。

本部分的练习有两项。第一项是排查脏数据：读者应在知识库中找一段含全角字符或零宽字符的文本，指出清洗之后它会变成什么样。第二项是判断去重策略：读者应说明为什么近似重复只记日志而不丢弃，并给出一个总则与品类例外同时被召回的例子。

本篇对应的指标是第 11 部分"评测体系"中的检索 Recall@3。清洗与去重直接影响哪些切片能够进入候选集，而 Recall@3 衡量的正是"相关政策有没有进上下文"。读者在阅读第 4 部分"召回"时，可以回到本篇确认检索对象的来源与质量。
